# PvPokeのレベル・個体値付きメタの取り込み

## 確認した原因

提示されたCSVは87行あり、15行目furretから一部の15行が `species,fast,charged1,charged2,level,atk,def,hp` の8列。アップロード処理が4列限定のため、15行目で拒否していた。前回の重複統合とは別の原因。

列数を整理した後は16行目grumpigのRETURNも拒否された。PvPokeの `Pokemon.js` はGameMasterのchargedMovesに加え、shadoweligibleタグがありlevel25CPがリーグCP上限以下の種にRETURNを、shadowタグの種にFRUSTRATIONを追加する。Python側の検証は元のchargedMovesだけを見ていた。

提示された全文を `tests/fixtures/meta_pvpoke_mixed_columns.csv` に保存して再現。公式GameMaster（timestamp `2026-10-26 22:08:07`、blob SHA `f5a1c50c9162fac0f0c34bb7a662f995c6506b74`）から当該68種の検証・準備に必要な項目を抽出し、テスト用データとして出典付きで固定した。本番アカウントのデータは読み書きしていない。ChatGPT用PvPoke MCPには接続していない。

## 実装と使い方

- ファイル読み込みと直接貼り付けで4列・8列の混在を受付。8列目までの数値を検証してから先頭4列を取り込む。レベルは1〜51の0.5刻み、個体値は0〜15の整数。NaN、無限大、不足・余分な列、不正技は拒否する。
- 保存前に「レベル・個体値付き15行」と対象行を表示し、入力のレベル・個体値を保存・計算に使わないことを明示する。種と技だけを保存し、相手の個体値は既存の選択条件（default/rank1/attack/defense）で生成する。入力レベル51を許容しても、計算上限50は変更しない。
- 同じ種と技構成は先頭の1行へ統合。入力個体値が異なっていても同じ技構成に統合する。技違い・通常/シャドウは保持。個体値を固定した相手としての保存・再出力には対応しない。
- 条件付きゲージ技の共通ヘルパーを、Webカタログ、メタ検証、計算準備で使用。GameMaster自体は書き換えない。RETURNを全種へ無条件に許可しない。
- 「カスタムメタを追加」→名前と全文を入力→「貼り付けた内容を確認」→注意と件数を確認して「別のプリセットとして保存」。ファイルの場合も同じ処理を使う。

## 設計の比較・学習ポイント

任意の余分な列を黙って削る実装は短いが、列の取り違えを見逃す。今回は対応する4/8列を明示し、値を検証した上で保存対象を確認画面に示した。

8列をそのまま保存して個体値を固定する案は、計算モード、重複判定、保存形式、出力との整合性を変える。今回の「メタ一覧を取り込む」という目的には、入口で既存の4列形式へ揃える方法を採用した。固定個体値の再現が必要になった場合は別の仕様として設計する。

入力を扱いやすくする層と、計算用データの厳密な検証を分ける。保存済みデータのパーサーは4列のまま、確認と保存は同じ整理処理とSHA256を使う。これにより、後段を広く変更せずに外部形式へ対応できる。初心者が間違えやすいのは、画面だけで列を削ること、エラーの行番号を整理後の番号に変えること、RETURNをすべての種へ許可すること。今回の共通ヘルパーと境界値テストは自分で再実装すると学習効果が高い。

## 検証・性能・復旧

ローカルで提示87行→87技構成、個体値付き15行、技構成の欠損なしを確認。4モードで87件ずつ計348件を生成でき、除外0件。既存Nodeエンジンで1候補×87相手×6シールド条件＝522対面を実計算して成功した。対戦結果の妥当性を人手で全件照合したという意味ではない。

同じローカル環境で87行の入力整理を1000回実行し、平均約0.285ms。4モードの準備は約3.096秒、522対面のNode計算は約0.535秒。単一実行環境での参考値であり、本番での速度保証や改善率ではない。変更前はこの入力がエラーとなるため、同じ処理の成功時との速度比較はできない。取り込みは入力行数に比例し、追加通信なし、80KB・500技構成の上限を維持。

最終の回帰テスト件数・Dockerビルド・Chromium QA・本番反映は当該PRの結果を参照。Android実機の貼り付け、ログイン済み本番画面での提示データ保存は未実施。

既存メタ・履歴・デフォルト・お気に入りを移行・自動更新しない。追加ライブラリ・API・保存スキーマ変更なし。異常時は既存データを維持。復旧は当該コード変更をrevertして再配備する。保存済み4列データは旧版でも読めるが、旧版は条件付きRETURNの検証で再び拒否するため、元版に戻すと取り込み問題も再発する。
