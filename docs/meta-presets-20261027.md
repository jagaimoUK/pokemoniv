## 原因と設計判断

旧実装は `project_meta_opponents.csv` という単一アップロード先を `os.replace` で更新していた。プリセットの識別子・一覧・設定を保持する仕組みがなかった。

| 選択肢 | 判断 |
|---|---|
| ブラウザのlocalStorageだけに保存 | 端末を替えると見えず、ブラウザ消去で失われるため不採用 |
| 新規DBや外部サービス | 既存は単一ワーカーで最大50件。追加依存と移行負担が大きく不採用 |
| 既存永続ボリュームにJSON保存 | 名前・CSV・デフォルト・お気に入りを1つの原子的更新で保持できるため採用 |
| 選択のたびに共通CSVを上書き | 別タブやMCPに影響するため不採用 |
| 計算ごとに選択IDとSHA256を固定 | 既存MCPとの互換性を保ち、連続計算の条件を固定できるため採用 |

`pvpoke_meta_presets.py` が保存・検証・一覧・スナップショットを担当。画面はIDを保持し、APIが名前や内容を管理する。表示は `textContent` を使う。

保存は既存のサーバー実行ロック内で、revisionを照合→全データ検証→一時ファイルへ書込・fsync→os.replace。保存前の正しいJSONを `.bak` に保持。不正JSONを空の設定として上書きしない。別タブの古いrevisionは拒否する。

計算開始時もサーバーロック内でGameMasterに対する全行検証とSHA256照合を行い、内容のハッシュを名前にしたCSVを生成。バックグラウンド処理にこのパスを直接渡す。共有の旧CSVは変更しない。途中再開もIDとハッシュを引き継ぐ。古い再開データにIDがなければ従来の挙動を維持する。

## 保存先と復旧

既存の `archive_dir(work)` を使用。Railwayでは既設 `/data` ボリューム上の `pvpoke_archives/meta_presets.json` と `meta_presets.json.bak` に保存する。個別計算のCSVは同じ配下の `meta_snapshots/<sha256>.csv`。

コードの復旧は変更コミットのrevertと旧版の再デプロイ。旧CSV・履歴に移行を行わないので旧コードでも従来メタを利用できる。新設定は削除せず保持。JSONの復旧が必要な場合だけ、アプリ停止中に現在の不正ファイルを退避し、`.bak` の内容を検証して原子的に置換する。自動復元はせず、破損を見逃さない。

## 学習のポイントと共通開発原則

1. **IDと名前を分ける**: 名前は表示用、IDは参照用。同じ内容や似た名前でも混同しない。
2. **デフォルトと今回の選択を分ける**: ファンタジーを1回選んでも普段の設定は変わらない。永続設定と画面内の一時状態を分離する。
3. **楽観的ロック**: revision 3の画面で保存しようとして、既にサーバーが4なら拒否する。後勝ち上書きによるデータ消失を防ぐ。
4. **原子的保存**: 書きかけの本ファイルを作らず、完成した一時ファイルと入れ替える。バックアップとは目的が異なり、両方必要。
5. **不変の計算入力**: 計算開始後に元設定が変わっても、渡したスナップショットは変わらない。結果の再現性を確保する。
6. **根拠のある最適化**: 実測→重複解析を発見→内容をキーにした上限付きキャッシュ→再測定。設定やファイルそのものを無条件でキャッシュしない。
7. **失敗の契約も設計する**: 通常系だけでなく、古い画面、満杯のディスク、不正データでも元データを守る。

自分で実装すると学習効果が高いのは、`save` のrevision照合と原子的書込、`snapshot` のハッシュ照合、そして「古い画面から保存しても新しい設定が消えない」テスト。小さい機能でも、画面→API→保存→計算のデータの流れを一貫して追う練習になる。
