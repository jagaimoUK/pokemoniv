# 相手の技・IV感度を構築へ反映

基準: main `f0a24c17f8e52f281d93e056ff159f2c339d7b80`、PR #85の詳細統合後。
設計書の優先度3について、相手の条件変更に対する上位候補の感度比較を追加する。
従来はメタの技構成・標準IVでの対応を評価しており、別の合法技や攻撃寄りIVで対応役が変わることを構築順位へ反映していなかった。

## 機能と評価順

- 「相手の技・個体値が不明なときの比較」で有効にする。初期状態は無効で、従来の処理経路を維持する。
- 静的探索・既存の詳細統合が終わった最大3案で、共通の相手を比較する。通常分析では現在の6体だけを比較できる。自動補完にも対応する。
- 重要度上位2グループ、同重要度なら静的対応が弱い相手を優先する。重み0のグループは計算しない。
- 各グループは基準技構成と追加仮説・既存メタから最大2構成を採用する。任意の追加入力は8件までで、日本語・英語の既存エディターと技の合法性検証を再利用する。無制限の全技組合せ生成は行わない。
- 各技構成を、入力・標準IV、積最大、実攻撃最大、実防御最大の4条件で比較する。既存IVセレクターの入手下限、レベル制約、RETURN条件を再利用し、各条件をCP1500/Lv50へ再正規化する。同一条件は統合し、調べた技・IV・Lv・CPを表示する。
- 技仮説ごとに都合のよい担当を選ぶと頑健性を過大評価する。このため、各担当の仮説内最小Ratingを先に求め、その後で担当を選ぶ（`max担当 min仮説 Rating`）。相手の隠れた技ごとに担当を切り替える `min仮説 max担当 Rating` は使わない。
- 静的評価の未計算重み・未対応重み・深刻度を優先し、その条件が同等の案を「固定担当が不足する標本内重み」「固定担当の最悪Ratingの加重値」で比較する。標本内の全条件でRating>500となる担当が1体だけの場合、外すと失われる役割を表示する。
- 順位変更前後と各案の指標、担当ごとの最小・最大Rating、変動幅を表示する。一部でもunknownなら全案の感度比較前順位を維持する。未計算を敗北や0点に置き換えない。
- 1体だけの交換候補の順位は従来の静的評価。別の最終案を反映する操作と固定枠を維持し、感度比較前の詳細結果は折り畳んで参照できる。

標準PvPoke・双方HP満タン・シールド2-2を用いた条件感度の参照値であり、技非公開での実行可能な単一行動方針や3対3勝率ではない。
4つのIV条件も出現確率を表さず、全IV・全技・全メタへの対応保証はしない。対象外の追加入力、採用した技構成数、未評価条件を表示する。

## 計算量・データ保護

基準6体と最大3案の和集合24体 × 相手2グループ × 技2構成 × IV4条件 = **最大384セル**。
メタ500行・全24体のテストで上限384を確認する。既存の詳細統合300要求とは別の任意の追加予算であり、双方有効なら最大684要求となる。
正規化後に同一になるIV条件やゲージ技の順序だけが違う仮説は重複計算しない。

実際の対面は既存の詳細戦略SQLiteキャッシュ・ジョブ内メモ化を再利用し、同じ標準詳細条件との重複も避ける。
キャッシュは既存の16 MiB上限を継承する。重要度は計算セルのキーに含めず、条件が同じなら加重集計だけをやり直す。
IV準備のLRUにもポケモンデータ、CPM、技、CP・レベル制限を含めるため、別条件のIVを流用しない。

保存JSONへ `opponent_uncertainty` と `opponent_hypotheses` を追加するだけでDB移行は不要。
旧保存データでは無効として読み込む。入力IV・技構成・保存パーティ・結果ZIP・認証設定・永続ボリュームは変更・初期化しない。
計算要求のスナップショットに今回の有効条件も含め、条件を変更した古い結果を反映しない。
メテノは固定戦略未対応のままunknownとし、不正確な戦略で代用しない。

## 測定

`PYTHONPATH=.:tests python tests/benchmark_party_uncertainty.py`。
固定GameMaster、7候補・メタ6行・相手2グループ・追加技1件、独立SQLiteで各3回の中央値。
比較元と追加機能の双方で既存の詳細戦略統合を有効にした。同一環境内の標本であり、本番全メタの所要時間は未測定。

| 条件 | 完了時間 | 感度セル要求 | 新規感度対戦 | 感度キャッシュ再利用 |
|---|---:|---:|---:|---:|
| 既存の詳細統合・初回 | 1.7338秒 | 0 | 0 | 0 |
| 既存の詳細統合・再利用 | 0.3069秒 | 0 | 0 | 0 |
| 感度比較も有効・初回 | 2.3093秒 | 84 | 70 | 14 |
| 感度比較も有効・再利用 | 0.5332秒 | 84 | 0 | 84 |
| 固定枠1体のIV変更 | 1.1962秒 | 84 | 10 | 74 |
| 正規化後の対象が同じ重み変更 | 0.5977秒 | 84 | 0 | 84 |
| 追加技仮説を1構成変更 | 0.9333秒 | 84 | 28 | 56 |

初回の差は約0.576秒、再利用時の差は約0.226秒。この値をキャッシュなしの実戦計算速度とは扱わない。
正規化された条件や比較する案・相手が変われば新規セルの計算が必要になる。

## 検証と次の段階

- 単体・統合: 実エンジン、合法技・4IV、同一条件統合、入力不変、固定担当の評価順、順位逆転、静的な唯一対応の保護、unknown保持、ゼロ重み除外、384セル上限、キャンセル、キャッシュ、入力検証、保存・復元。
- ブラウザー: 実認証ゲートウェイ＋ローカルエンジンで日本語技入力、任意設定の保存・復元、候補反映、再計算0件、360/390px幅を確認する。ジョブIDを待つ既存の待機方式を維持する。
- Docker・セキュリティ・既存全回帰はPR CIで確認する。

未完了: 全技/全IVを対象にした頑健性保証、追加の交代タイマー・再交代・残り2体の連携、大会ルール変更、手動補完タグと役割を守る交換探索、完全3対3、メテノ固定戦略、Android実機・本番認証下の全操作。
次は交代状態モデルと大会ルールの設計を個別に扱う。CP制限は既存の最適化・JS計算・キャッシュ・UIにまたがるため、入力欄だけの変更で対応済みにしない。

再利用できる設計上の要点は、重い一次探索後に予算付きの感度比較を置くこと、担当と不確定条件の評価順を明示すること、集計条件と計算キャッシュを分けること。
