## 1. 目的・用語

イベント中の負担を減らすため、既存個体の重複読み取り、重複対戦計算、Pokémon GO内の名前・タグ変更を最小化する。最新厳選一覧の中心は**重要個体と同等の代替候補**であり、非重要個体を将来のメタ変化に備えて無制限に蓄積することは目的ではない。

- **厳選結果**：種族・評価対象フォルム別の重要個体・同等代替候補と推薦理由、対面、育成目標。最新結果と過去の版を区別する。
- **重要個体の個体記録**：実際に保有していると確認された個体の観測値、短い名前、タグ操作状況、履歴、育成目標。候補IVという理論上の組合せと実保有個体を区別する。
- **一時読み取り記録**：今回の読み取り・計算・操作・同期を再開するための非重要個体の情報。所持台帳の永続確定記録ではない。
- **対戦計算キャッシュ**：条件と計算版が合うセルのみを再利用する独立した計算成果物。個体の保有・博士送りの証明には使わない。
- **未確認**：同一個体・操作成功・CP挙動などを十分に検証できない状態。推測で確定扱いしない。

## 2. 全15問の確定仕様（要求）

| No. | 分野 | 確定仕様・境界 |
| --- | --- | --- |
| 1 | 進化形・メガ候補 | 読み取った進化前個体から到達可能な通常進化形・メガ形態も評価。評価対象形態と**実際に所持する形態は区別**。対象外の進化経路を創作しない。 |
| 2 | 70点判定 | 通常スーパーリーグ（GL）およびメガGLの**種族・形態のPvPoke総合ランキング**を両方参照し、**いずれかが70以上（OR）**なら候補を残す。片方の低評価のみで切り捨てない。全種モードは70点で除外しない。SCP順位やBattle Ratingをそのままこのランキング点と混同しない。 |
| 3 | スーパーMAXとCP/PL | スーパーMAX時のPL補正（通常MAXよりPL+2という想定）について、**未確定の2仮説を別結果として比較**する。CP・対面・目標PL・必要なアメXLの差を明示する。計算仮説をゲーム内確定事実として表示しない。 |
| 4 | メガ段階 | メガレベル4段階を選択でき、既定の優先比較はMAXとスーパーMAX。他2段階も指定できる。段階による技威力・CP/PLへの効果は実装前に根拠を確認する。 |
| 5 | パーティ作成・対戦 | 6体登録時は複数のメガ候補を許す。3体選出・対戦時は**大会・カップ固有の合法性**とメガ許可数を検証する。全ルールで一律1体と仮定しない。 |
| 6 | 永続結果 | **種族・評価対象形態別の最新重要個体一覧**と**重要な実個体ごとの記録・評価履歴**を別管理。通常の直近セッション履歴だけに依存しない。 |
| 7 | 重複読み取り | 種族・形態、IV、CP、取得できれば捕獲日・現ニックネーム等を照合し、「同一確認／一致可能性あり／新規」を区別。曖昧でも読み取り・安全な一時保存は継続し、別個体を自動統合しない。 |
| 8 | 差分計算 | 新規個体の取り込み完了を契機に、有効キャッシュで対面を再利用し未計算分を追加。**保存中の候補＋今回の新候補全体で**推薦（唯一の勝ち筋・劣後・代替性等）を再評価する。スキャンの各フレームで毎回再計算しない。 |
| 9 | ニックネーム | 既定は短く安定した個体識別用の固定名。設定「評価を付ける」「対戦相手も付ける」を個別ON/OFF、**初期値はいずれもOFF**。評価変化や設定変更のみで既存名を自動改名しない。GOの12文字上限・安全な変換と衝突に対処する。 |
| 10 | 検索オーバーレイ | 改名・タグ付け・整理候補などを分類し、**未完了かつ実際に操作が必要な個体のみ**送る。中断後は未完了から再開。GOでの検索成功と、名前/タグ変更成功を別々に確認。GOでの博士送りを自動実行したことにはしない。 |
| 11 | メタ・ゲーム更新 | 旧版の重要個体結果を保持し、影響する候補・対面だけ計算版照合後に再評価。完了まで「再評価が必要」と表示。影響範囲を証明できない場合は保守的に再評価へ含める。 |
| 12 | 履歴の保存先 | **Web側が正本**。Androidはオフライン時の未送信データを保護して一時保存し、再接続時に同期。既存データ互換とバックアップ・復元を確保する。 |
| 13 | 博士送り状態 | **博士送り済みの独立台帳は作らない**。重要個体から外れたことを実際の博士送り完了と同一視しない。`send`タグだけでも博士送りの証明にはならない。ユーザーの明示操作なしに送付しない。 |
| 14 | 非重要個体の一時記録 | 計算、必要な操作、Web同期がすべて完了後に一時記録を整理。**未完了・未同期・競合保留・失敗データは保護**。既存永続データはこの仕様だけを根拠に無断削除しない。 |
| 15 | Web/Android同期の競合 | 同一個体と十分確認できるときだけ項目単位で変更を安全に統合。**同じ項目の競合のみ保留**し、無関係な項目は進める。未同期の変更は通信断・再送後も失わない。 |

### 2.1 推薦とGO操作を必ず分ける

| 状態 | Web最新重要個体一覧 | Android検索オーバーレイ |
| --- | --- | --- |
| 新規重要個体、未処理 | 表示 | 必要な名前・タグ処理を表示 |
| 重要個体、変更なし・全操作完了 | 表示 | **表示しない** |
| 再計算で評価のみ変わり、必要なGO操作なし | 最新評価に更新 | **表示しない** |
| 名前は固定のまま、タグだけ未完了 | 表示 | タグ操作のみ表示 |
| 推薦から外れた個体 | 現在の重要一覧から外し、必要に応じ旧評価を参照可能 | 保護判定を経て整理候補としてのみ扱い、博士送り済みと断定しない |
| 同一性不明・検索が複数一致 | 安全な記録・再確認待ち | 誤命名/誤タグ付けを防ぐため停止 |

検索式の範囲確認、フォーム・シャドウ判定、手動/自動切替、連続実行の二重発火防止を既存の安全要件から後退させない。

### 2.2 最新結果の範囲と一時記録

例：ヤミラミを20匹読み取り、重要/同等代替が3匹の場合、**最新重要個体一覧の中心は3匹**。その他17匹を将来のメタ更新用に永続保持しない。処理中だけ必要な情報を保持し、計算・操作・同期の終了後に一時記録を整理する。

再評価対象は「保持中の重要/同等代替候補＋今回新規に取り込んだ候補」であり、既に整理した非重要個体を再評価できるとは主張しない。

### 2.3 育成目標の表示

一覧では `PL30まで強化が必要`、`強化不要` のように短く表示。PLは説明用の数値であり、固定値ではない。詳細には必要なアメ/アメXL/すな、実保有個体の現在PL/CPと評価形態の目標PL/CP、スーパーMAX補正の仮説・不確実性を記録する。ゲーム内で元に戻せないレベル変更を要求しない。

## 3. メガシンカCP計算：通常・一時ダウンスケーリング・スーパーMAXを分ける

**異なる3種類の値を混ぜない。**

1. **通常形態とメガ形態の理論CP**：対象形態の種族値、同じIV、レベル、ゲームデータ版から計算。進化前の実測CPとメガ後のCPを同一視しない。
2. **メガGL等の対戦時一時調整**：公式2026年告知は、対象メガ個体がリーグ上限を超える場合に**対戦中のみCPを一時的に減らし、終了後元に戻す**ことを明記している。https://pokemongo.com/en/news/go-battle-league-twilight-trails ／ https://pokemongo.com/news/more-mega-updates-2026 。実際の刻み・適用範囲・表示と計算の一致はカップごとに再検証する。
3. **スーパーMAXのPL+2と特別補正**：ユーザーが比較を希望した2仮説の対象。公式に確認できない部分は「仮説1／仮説2」と記し、補正の適用順序・上限CPとの相互作用・目標PL・必要なアメXL・戦闘計算の差を**実機と既存計算エンジンで検証するまで確定しない**。

**要件**：メガGLの対戦時ダウンスケーリングが有効なら「現在PL/CPが上限を超えたから参加不能」と即断しない。他方、低PL個体を対戦時に自動で**アップスケーリング**すると仮定しない。厳密な無補正大会ルールでは別の適格性を判定する。3体選出時のカップルールも独立評価する。

**最新コード調査の起点**：https://github.com/jagaimoUK/pokemoniv/pull/130 の最新 `[AI-HANDOFF v1]`。2026-11-25時点で `pvpoke_mega.py` と `pvpoke_ownership.py` に `allow_cp_downscaling` や `needs_power_up` の実装報告があるが、**Web全UI・全技構成・全リーグ・実機の完全対応を意味しない**。PRのHEAD/CI/未検証事項を毎回確認する。

**別の計算論点**：メガ専用の追加ゲージ技とメガレベル別の技倍率、シャドウがメガ化できない制約、メガ/ゲンシの形態マッピング、4段階の効果、CP/PLの上限、対面条件とキャッシュキー。古い通常形態の結果をメガ形態へ誤流用しない。

## 4. 保存と同期のデータ契約（詳細スキーマはコード照合後に確定）

概念上は次を分離する。**ここに挙げるキー名は設計上の論理名であり、既存APIの実際のJSON項目名とは限らない。**

- `selection_snapshot`：種族・フォーム・リーグ・計算条件・メタ版・推薦版、重要IV/代替候補、推薦理由、対面、最終評価時刻、鮮度状態。**評価結果の版**。
- `owned_individual`：確認済み個体ID、読み取り観測（種・フォーム・IV・CP・捕獲日等）、現在名/タグ、ユーザーが確定した育成目標。**所有状態の証拠**と理論候補を分離。
- `reader_pending`：Androidの操作種別、要求ID、対象ID、基準リビジョン、状態（未送信/競合保留/確認待ち/完了）、取得時刻。未確認の操作を完了にしない。
- `selection_job`：今回入力された候補、一時的な非重要候補、計算済みセル、同期・GO操作の完了条件。**未処理中は消さない**。
- `matchup_cache`：対象フォーム・技・IV・PL/CP・シールド・メガ段階/特別技・補正シナリオ・PvPoke/GM版を識別し、一致する場合のみ再利用。

**既存実装の事実**：PR #124は通常GLの `selection_snapshots_v1` / `selection_instances_v1`、`individual_sync_fields_v1` / `individual_sync_receipts_v1` を報告している。https://github.com/jagaimoUK/pokemoniv/pull/124#issuecomment-7082139935 。この既存スキーマを調べずに別の保存基盤を新設しない。Androidの最新開発正本は `PokemonIVReader-public-ci` の `main`；過去の `PokemonIVReader` masterを現行実装と誤認しない。

**同期の原則**：強い同一個体照合ができない場合、データ統合もGO自動操作も行わない。項目ごとに元の版と更新後の版を比べ、衝突項目のみ保留。リクエストIDで再送を冪等化。競合・未送信を解決する前に関連する端末記録を消さない。設定・学習データ・署名済みインストール環境・バックアップ形式を保護する。

## 6. 実装・検証順序（依存関係順、同じ機能の再実装はしない）

1. **現状棚卸し（読み取り専用）**：Web PR #124の実装済み通常GL履歴・差分計算・同期、Android現行 `public-ci/main`、Web PR #130のメガ基盤、各ブランチ最新 `AGENTS.md` とPR引き継ぎを照合。既存データと自動デプロイ経路を確認。
2. **重要個体保存の不足だけ補完**：既存永続スナップショットを再利用。最新結果・過去版・評価鮮度・個体記録の未対応部分のみ最小変更。
3. **新規読取→差分計算→推薦再評価**：通常GLで縦の一連の処理を実証。自動読取と手動保存候補統合の既存仕様に差がある場合、無断で統一せず差異を報告。
4. **同期・操作差分**：未送信保護と確認済み個体同期を使い、固定名・設定2スイッチ・タグ等の必要操作だけを送る。安全に処理できない個体は保留。
5. **メガ・ゲンシ形態とCP**：PR #130の基盤を利用し、通常/メガGLランキングOR、参加可否、ダウンスケーリング、4段階、スーパーMAX2仮説、育成目標とアメXL表示。
6. **6→3パーティ・対戦との接続**：大会ルールを使った選出合法性、メガ段階・技構成・計算キャッシュ互換を確認。無関係な対戦シミュレーターの再設計はしない。
7. **検証**：構文・静的→変更点単体/合成スモーク→必要範囲の回帰→隔離Web/Android実機。バックアップ復元・削除・本番反映は事前承認と適切な安全確認が必要。

第1段階の最小受入例：ヤミラミの既存重要個体2匹と新規候補1匹を、同一条件で差分計算・全件計算して推薦一致を確認し、**処理済みにはGO操作を出さず**未完了の名前/タグだけを再開できること。メガ計算の受入例は別試験とし、通常GL成功をメガGL成功とみなさない。
